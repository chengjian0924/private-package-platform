## 一、评审结论摘要

### 1.1 总体判定

安全校验模块的**核心架构成立**：以 `PackagesService.insertVersion()` 作为唯一入库收口，扫描前置、失败关闭（fail-closed）、按等级分流，报告与审计链路完整，32 个 e2e 用例全部通过。但评审发现 **2 项严重问题、14 项重要问题**，其中两项会导致「正常包被批量隔离」或「全量版本被误隔离」，属于会直接破坏生产可用性的缺陷。

**判定结果：需补充修订后重新评审，不可直接进入下一开发阶段。**

- 平台主链路（登录、发布、消费、导入、缺失补包、审计）可继续迭代；
- 安全校验模块冻结在当前状态，完成 P0/P1 整改并通过指定回归项后再申请复审。

## 三、分维度评审结论

### 3.1 需求匹配度（80/100）

| 需求 | 覆盖情况 | 结论 |
| --- | --- | --- |
| 格式与完整性 | 文件头/扩展名、归档结构、路径穿越、重复条目、嵌套归档标识、sha256、签名 | 基本满足；嵌套归档仅告警不深扫（RV-06） |
| 恶意代码 | MAL-001~012，覆盖反弹 Shell、编码执行、挖矿、破坏性命令等 | 静态规则可落地；能力边界未声明（RV-28） |
| 已知漏洞 | 本地漏洞库 + 自研版本区间匹配 | 依赖区间误判（RV-02）、无传递依赖（RV-12）、空库仍通过（RV-07） |
| 权限风险 | PERM-001~010，安装脚本、setuid、`.pth`、容器高权限等 | 满足；原生二进制策略过严（RV-21） |
| 敏感信息 | SEC-001~010，密钥、令牌、口令、JWT、连接串、PII | 满足；证据脱敏不完整（RV-10） |
| 行为风险 | BEH-001~009，外联、写系统路径、动态加载、原生二进制 | 满足静态预判；无法覆盖运行时行为，需在文档中明确 |
| 上传后自动触发 | `insertVersion` 统一闸门，BLOCK/QUARANTINE 不入库 | 满足；批量导入 strict 语义有缺口（RV-03） |
| 分级处置 | ALLOW/WARN/QUARANTINE/BLOCK + 阈值配置 | 满足；合格标识不可被消费方验证（RV-13） |
| 报告可追溯 | DB + JSON/CSV + 审计哈希链 | 基本满足；缺规则/漏洞库快照版本（RV-08）、CSV 注入（RV-11） |
| 定期复检 | 定时任务 + 手动复检 + 指纹对比 | 框架满足；签名上下文丢失导致误隔离（RV-01） |

**需求覆盖率评估：约 80%**。缺口集中在「依赖漏洞的真实性」「复检一致性」「整改信息回传」三处，均为用户可感知的关键路径。

### 3.2 技术可行性（76/100）

可行部分：

- 归档解析使用项目已有依赖（`tar`、`adm-zip`），未新增第三方包，部署无额外负担；
- 扫描在入库前同步完成，语义简单、无最终一致性问题；
- 本地离线漏洞库符合内网/隔离网环境约束；
- 指纹对比避免复检记录无限膨胀。

不可持续部分：

- 同步扫描放在 HTTP 请求内，缺少队列、并发上限与超时（RV-04）；
- 归档解析为整包内存模型，200MB 上限叠加多份拷贝，存在 OOM 风险（RV-05）；
- 复检通过 HTTP 同步执行全量版本，无法水平扩展（RV-04、RV-19、RV-20）。

### 3.3 架构合理性（72/100）

优点：

- **唯一收口**：全仓库仅 `insertVersion` 写入 `package_versions`，`skipSecurityScan` 仅用于隔离放行，闸门不易被绕过；
- 扫描与持久化解耦为 `evaluate()` / `persistScan()`，复检复用了同一判定逻辑；
- 处置策略集中在 `resolveDisposition()`，阈值可配置；
- 报告、隔离、审计、埋点的职责边界基本清晰。

问题：

- `SecurityService` 同时承担闸门、报告、隔离区、复检、统计，文件规模偏大，单测困难；
- `rules.ts` 超过千行，规则与执行器耦合，规则版本硬编码为 `'2026.11'`，无法按规则包灰度/回滚（RV-08、RV-32）；
- 数据模型缺少规则包版本、漏洞库快照标识、外键约束，审计可复现性不足（RV-08）；
- 扫描器与被测包共享进程，缺少资源隔离（RV-05）。

### 3.4 性能指标（52/100）

当前事实：

- 单次扫描在请求线程内串行执行，文本规则为同步正则；
- 读包、解压、规则匹配存在多份内存拷贝；
- 复检按版本串行全量扫描，无并发上限；
- 无扫描耗时/队列长度/失败率指标端点，仅有事件埋点；
- 无压测或容量基线。

风险：

- 大包上传 P95 延迟不可控，易触发网关超时；
- 并发上传时事件循环被正则匹配占用，影响其他接口；
- 复检窗口内 CPU 与内存尖峰，可能影响发布与下载。

结论：性能设计**不达标**，需补充目标、队列与隔离执行（RV-04、RV-15）。

### 3.5 安全合规性（62/100）

做得好的部分：

- fail-closed：扫描异常不放行；
- 密钥类证据默认掩码；
- 隔离区与私有源物理分离；
- 审计动作齐全，日志具备哈希链；
- 控制台输出统一转义，未发现 XSS。

主要问题：

- 依赖区间误判造成「过度隔离」，本质是安全策略正确性缺陷（RV-02）；
- 复检丢失签名导致「全量误隔离」（RV-01）；
- CSV 报告可被公式注入，直接威胁管理员终端（RV-11）；
- 恶意代码证据未统一脱敏，可能把敏感串写入报告（RV-10）；
- 漏洞库为空时仍给出「通过」，形成合规假象（RV-07）；
- 报告缺少规则/漏洞库快照版本，无法证明「当时按什么规则判定」（RV-08）；
- 上传者拿不到整改建议，不满足「返回用户整改提示」（RV-09）。

### 3.6 可维护性（64/100）

- 规则以常量数组维护，新增规则成本低；
- 但规则与执行逻辑同文件、无规则 schema 校验、无规则单测；
- 报告字段散落在 service 与 controller，CSV 表头与 JSON 字段易漂移；
- 关键分支缺少测试：`requireSignature=true` 的复检、空漏洞库、strict 批量、并发复检、压缩炸弹；
- 文档与实现的边界描述不一致（如低危维度状态）。

### 3.7 用户体验适配性（66/100）

- 管理员侧：概览、筛选、详情、整改建议、报告下载、隔离放行/废弃、漏洞库导入、手动复检形成闭环，体验完整；
- 开发者侧：上传被拦截时只能看到通用文案与 `scanId`，npm 通道甚至没有 `scanId`，无法自助整改（RV-09）；
- 列表固定 `pageSize=100`，无分页与总数，数据量增长后不可用（RV-27）；
- 隔离区按 sha 去重，同文件多版本只显示一条，易误判（RV-17）；
- 漏洞库仅有导入与计数，无条目浏览与快照信息（RV-33）。

## 四、模块逻辑完整性核查

| 模块 | 核查结论 | 关联问题 |
| --- | --- | --- |
| 归档解析 | npm/sdist 走流式 tar，wheel/zip 走 AdmZip；路径穿越、重复条目、嵌套归档可识别；缺少压缩比与真实解压上限 | RV-05、RV-06 |

## 五、问题清单（分级）

> 证据列给出关键文件与函数；影响列描述可复现的业务后果；优化方向均为可落地方案。

### 5.1 严重（P0，必须修复）

| 编号 | 问题 | 证据 | 影响 | 优化方向 |
| --- | --- | --- | --- | --- |
| RV-01 | 定期复检丢失签名上下文，开启强制签名后会把全部存量版本判为高危并隔离 | `security.service.ts` 的 `runRescan()` 构造 `ScanInput` 时未传 `signature`；`rules.ts` 的 `verifySignature()` 在 `requireSignature=true` 且无签名时产生 `INT-SIG-001`（high）；复检按 quarantine 阈值自动改 `status='quarantined'` | 生产开启 `SECURITY_REQUIRE_SIGNATURE=true` 后，一次定时复检即可让全部 `active` 版本从私有源消失；原本验签通过的包报告也会变成 `unsigned` | ① 在 `package_versions` 或 `security_scans` 持久化签名与验签结果（`signature_status`、`key_id`、`signature`）；② 复检优先复用持久化签名重新验签；③ 无法取得签名时输出 `unknown` 而非 high，且签名类问题单独策略化，默认不触发自动隔离；④ 补 `requireSignature=true` 的复检 e2e |
| RV-02 | 依赖漏洞按「非精确区间即可能受影响」处理，导致正常包被大面积隔离 | `vuln.service.ts` 的 `dependencyMaybeAffected()` 对任何非精确版本声明直接返回 true；命中后取该依赖所有 advisory 的最高等级，常见 `^4.x`、`>=1.0` 声明会命中全部历史漏洞 | 例如声明 `lodash: ^4.0.0` 的包，即使实际锁定 4.17.21，也会因 `<4.17.21` 的旧漏洞被判 high → QUARANTINE；正常发布被系统性阻断，团队会关闭校验或绕过闸门 | ① 解析 `package-lock.json` / `pnpm-lock.yaml` / `yarn.lock` / `poetry.lock` / `Pipfile.lock` 获取解析后版本，按真实版本匹配；② 无 lockfile 时对依赖类漏洞降级为 WARN 并标注「未解析实际版本」；③ 实现 npm `semver.intersects` 与 PEP440 区间求交，仅在区间相交时命中；④ 自包漏洞与依赖漏洞分级策略分离；⑤ 用合成 advisory 覆盖「已修复版本不应命中」用例 |

### 5.2 重要（P1，下一阶段前应闭环）

| 编号 | 问题 | 证据 | 影响 | 优化方向 |
| --- | --- | --- | --- | --- |
| RV-03 | 批量导入「校验」阶段不执行安全扫描，strict 模式对安全拦截不具备原子性 | `import.service.ts` 的 `validate()` 仅做结构校验即标记 VALID；安全扫描发生在 `commit()` 的 `insertVersion()`；catch 将 SEC_BLOCKED/SEC_QUARANTINED 记为条目 FAILED 后继续处理后续条目 | 批次页面显示 100% 校验通过，提交后部分条目失败；strict 模式仍产生部分入库，与「全有或全无」预期不符，需人工对账 | ① `validate()` 阶段按 sha 预扫描并缓存结果，commit 复用；② strict 模式在写入前完成全部安全判定，任一 BLOCK/QUARANTINE 直接终止且零写入；③ 批次统计增加「安全拦截」状态；④ 补 strict + 安全拦截 e2e |
| RV-04 | 扫描在 HTTP 请求线程同步执行，无队列、并发上限、超时与背压 | `packages.service.ts` 的 `insertVersion()` 直接 `await scanAndGate()`；`registry-pypi` 使用内存 multer，body 上限 200MB；复检接口同步返回 | 大包上传 P95 不可控，网关易 504；并发上传时同步正则占用事件循环，拖慢其他接口；复检请求长时间挂起 | ① 扫描迁移到 worker_threads / 子进程，主线程只排队与等待结果；② 队列设置并发上限、排队超时、单包扫描超时；③ 复检改为后台任务，接口返回 202 + runId；④ 暴露队列深度与扫描耗时指标 |
| RV-05 | 归档解析存在内存放大与压缩炸弹风险 | `rules.ts` 的 `readZipEntries()` 使用 `new AdmZip(buffer)` 与 `entry.getData()`，仅按声明的解压大小过滤；`maxScanFileBytes` 超限只产生 medium，不终止扫描 | 构造高压缩比或声明大小造假的 zip 可造成数百 MB~GB 级内存分配，触发 OOM，影响整个平台 | ① 增加压缩比阈值（如 >100:1 直接拒绝）与单条目真实解压硬上限；② 超过 `maxScanFileBytes` 直接拒绝而非告警；③ 改用流式 zip 解析并对解压缓冲区计数；④ 扫描进程设置内存上限，超限按 SEC_SCAN_FAILED 阻断 |
| RV-06 | 嵌套归档只标记不递归扫描 | `rules.ts` 的 `INT-008` 仅产生 medium finding；medium 对应 WARN，包仍可入库 | 将恶意脚本放入 `payload.zip` 再打入包内即可绕过全部恶意代码/敏感信息规则，实际防护形同虚设 | ① 递归扫描嵌套归档（建议深度 2~3，受总字节预算约束）；② 无法扫描的嵌套归档提升为 high 或直接 BLOCK；③ 报告标注嵌套路径 |
| RV-07 | 漏洞库为空时仍判定「通过」并生成合格记录 | `security.service.ts` 的 `buildDimensions()` 在 advisory 数为 0 时只写 summary，不改变 status；无 finding 即 pass，最终 ALLOW | 首次部署尚未导入漏洞库时，任何包都能拿到 ALLOW，形成合规假象，后续审计无法解释 | ① 空库时漏洞维度置为 `unknown`，整体至少 WARN；② 提供 `SECURITY_REQUIRE_ADVISORY_DB` 配置，未导入时禁止发布或强制告警；③ 控制台显示「漏洞库未初始化」醒目提示 |
| RV-08 | 扫描记录缺少规则包版本与漏洞库快照标识，报告不可复现 | 报告中 `ruleVersion` 硬编码为 `'2026.11'`；`security_scans` 无 `rule_version`、`advisory_snapshot_id` 字段；`vulnerability_advisories` 无导入批次表 | 无法回答「这次判定依据哪版规则、哪批漏洞数据」，规则调整或漏洞库更新后历史结论无法解释，不满足可追溯/可审计 | ① 新增 `security_rule_packs`、`advisory_snapshots` 表；② 扫描记录写入规则包版本、快照 ID/哈希、引擎版本；③ 报告固定输出三者；④ 复检差异按快照维度展示 |
| RV-09 | 上传者拿不到可执行的整改信息，权限模型过窄 | npm 错误响应仅 `{error, reason, scanId}`，`reason` 为通用文案；全局异常过滤器对 `/npm`、`/pypi` 丢弃 `details`；`security:read` 仅 admin | 开发者只看到「检出严重风险」，不知道哪条规则、哪一行、怎么改；PyPI 通道连 `scanId` 都没有，只能找管理员，闭环效率低 | ① registry 错误体附带 top 3 findings（规则、等级、位置、整改建议）与报告短链；② 增加 `security:read:own`，允许上传者查看自己上传包的报告；③ 报告短链使用一次性签名 token，避免开放全部记录；④ 文档补充开发者自助流程 |
| RV-10 | 证据脱敏不完整 | `rules.ts` 的 `runPatternRules()` 仅在 `rule.mask` 为真时调用 `maskEvidence()`；恶意代码/行为规则的 evidence 直接截取原始片段并入库、入报告 | 含令牌、内网地址、连接串的代码片段会进入 `security_findings`、JSON/CSV 报告与导出文件，报告本身成为泄露渠道 | ① 默认对所有 evidence 脱敏，仅保留规则命中特征；② 证据改为「文件 + 行号 + 匹配类型」，必要时展示掩码片段；③ 增加高熵字符串识别与统一替换；④ 报告导出前二次过滤 |
| RV-11 | CSV 报告存在公式注入 | `security.service.ts` 的 `csvCell()` 仅在含逗号/引号/换行时加引号，未处理以 `=`、`+`、`-`、`@` 开头的单元格；内容来自包内代码与文件名 | 管理员用 Excel 打开报告时可能触发外部链接、DDE 或恶意公式，形成针对安全人员的供应链攻击面 | ① 对以 `= + - @ \t \r` 开头的单元格前置 `'`；② 统一转义双引号；③ 增加 UTF-8 BOM 便于 Excel 正确识别；④ 补单元测试 |
| RV-12 | 仅匹配直接依赖声明，无 lockfile 解析与传递依赖，未生成 SBOM | `rules.ts` 依赖提取仅来自 `package.json` 的 dependencies / METADATA 的 Requires-Dist；`vuln.service.ts` 只按名称+声明区间匹配 | 真实漏洞大多位于传递依赖，当前方案会大量漏报；也无法向使用方提供成分清单，与行业实践（SBOM）不符 | ① 解析 lockfile 得到完整依赖树与实际版本；② 生成 CycloneDX/SPDX SBOM 并随报告存档；③ 漏洞维度按「直接/传递」分组统计；④ 无 lockfile 时明确标注检测深度 |
| RV-13 | 「安全校验合格标识」无法被消费方验证 | 合格仅体现为 `security_scans.disposition=ALLOW`，未写入 packument / simple index / 下载响应，也没有公开校验接口 | 需求要求「生成合格标识」，但 npm/pip 客户端与下游流水线无法确认包是否通过校验，标识只存在于管理端 | ① packument 版本元数据增加 `security: {status, scannedAt, scanId}`；② 下载响应增加 `X-Package-Security` 头；③ 提供按 `name@version` 查询的只读校验接口；④ 标识随复检结果更新 |
| RV-14 | 对象与隔离文件存在孤儿、双份与无回收 | 上传入口先 `storage.putObject()` 再 `insertVersion()`；扫描异常、重复版本、放行冲突时对象不清理；QUARANTINE 同时保留 `objects/` 与 `quarantine/` 两份；导入批次文件提交后不清理 | 长期运行磁盘持续增长；隔离区占用翻倍；对象与记录不一致，排障困难 | ① 建立对象引用计数与定期孤儿扫描任务；② 隔离改为 move 而非 copy；③ 放行/废弃使用事务或补偿清理；④ 批次完成后按策略清理 `batches/`；⑤ 增加磁盘水位告警 |
| RV-15 | 无性能基线与可观测指标 | 仅有事件埋点，无扫描耗时、包大小、条目数、队列深度、失败率指标；无压测记录 | 无法判断容量与 SLA，也无法在上线后定位性能退化；需求中的「性能指标」维度实际缺失 | ① 定义基线（如 10MB 包 P95 ≤ 2s、50MB ≤ 8s，待业务确认）；② 埋点记录大小/条目/耗时/命中规则数；③ 增加 `/metrics` 或导出到现有监控；④ 上线前完成并发压测 |
| RV-16 | 关键路径测试缺口 | 现有 6 个安全 e2e 未覆盖：`requireSignature=true` 复检、空漏洞库、strict 批量、嵌套归档、压缩炸弹、CSV 注入、并发复检、依赖区间相交 | 上述缺陷均可回归，当前测试无法阻止 RV-01/RV-02/RV-03/RV-05/RV-06/RV-07/RV-11 再次出现 | ① 为 `versionInRange()`、`dependencyMaybeAffected()` 增加表驱动单测；② 增加 8.2 节 10 项 e2e；③ 引入最小 fuzz 用例（畸形 tar/zip）；④ CI 保留全量测试 |

### 5.3 一般（P2，纳入近期迭代）

| 编号 | 问题 | 证据 | 影响 | 优化方向 |
| --- | --- | --- | --- | --- |
| RV-17 | 隔离区按 sha256 去重，隐藏同文件多版本记录 | `security.service.ts` 的 `listQuarantine()` 以 sha256 去重，只保留最新一条 | 同内容不同版本只显示一条，放行后旧记录再次出现，管理员误以为重复告警 | 按 sha 分组展示全部版本，支持批量放行；接口返回 `versions[]` |
| RV-18 | 放行非幂等、失败无回滚 | 控制器先 `putObject` 再 `insertVersion({skipSecurityScan:true})`，成功后标记释放；版本冲突时对象已写入且隔离记录未更新 | 重复点击或并发放行会产生 409 与残留对象，状态不一致 | 放行前预检版本是否存在；使用幂等键；失败时清理新写入对象；状态机增加 `releasing` |
| RV-19 | 复检并发无服务级互斥 | `scheduler.ts` 的 running 锁只防自身重入；手动复检接口直接调用 `runRescan()` | 定时与手动复检重叠，产生重复扫描记录、重复隔离与 CPU 尖峰 | 服务内互斥 + 数据库运行锁；冲突时返回 409 并提示已有任务 |
| RV-20 | 定时复检无持久化、无错过补偿、多实例会重复 | `setInterval` 启动后等待完整间隔；运行记录只有完成后写入；部署文档为单机 | 重启后长时间未复检；多实例部署时重复执行 | 持久化 `last_run_at`，启动时判断是否补跑；使用 cron 表达式；多实例用 DB 锁选主 |
| RV-21 | 原生二进制一律 high 并隔离 | `rules.ts` 的 `BEH-009` 对 `.node`/`.so`/`.dll` 直接 high | 含原生扩展的合法包（数据库驱动、图像处理）全部进入隔离区，运营成本高 | 按包名/发布者白名单；或降级为 WARN 并要求声明；提供「原生二进制例外」配置 |
| RV-22 | npm 多版本发布非原子 | `registry-npm.controller.ts` 循环插入多个版本，后续版本失败时前面已入库 | 客户端收到失败响应但部分版本已生效，重试触发重复版本错误 | 先完成全部版本的校验与预扫描，再统一写入；或限制单次仅一个版本 |
| RV-23 | npm 完整性校验逻辑偏弱 | 声明的 `integrity` 不匹配但 `shasum` 匹配时放行；`integrity` 匹配时不校验 `shasum`；附件 key 回退取第一个 | 可能接受内容与声明不一致的包，或把错误附件归属到版本 | 以 SRI `integrity` 为权威，不匹配直接拒绝；`shasum` 作为辅助校验；附件 key 必须精确匹配 |
| RV-24 | 版本区间语义不完整 | 自研 PEP440 比较忽略 epoch、预发布、post 发布；`!=1.0.*` 等通配比较不准确；不支持 RSA-PSS 验签 | 漏洞命中存在漏报/误报；部分合法签名被判失败 | 使用成熟实现（npm `semver`、Python `packaging` 语义移植）并补表驱动测试；验签支持 PSS 与 keyId 选择 |
| RV-25 | 漏洞库无来源校验与别名去重 | 导入仅校验 JSON 结构；唯一键包含 `affected_range`，同一 CVE 的 CVE/GHSA/OSV 记录会并存 | 同一漏洞重复计数、风险分虚高；被篡改的快照无法识别 | 快照附带 manifest 与校验和/签名；按 CVE/GHSA 别名合并；导入报告展示冲突与覆盖 |
| RV-26 | 报告与扫描数据无保留策略 | 每次扫描生成 meta 报告与 findings，按天复检长期累积，无清理任务 | 磁盘与 SQLite 持续增长，备份窗口变长 | 定义保留期（如 180 天）；按包保留最近 N 次；历史归档到冷存储 |
| RV-27 | 控制台列表无分页、筛选不全 | `app.js` 固定 `pageSize=100`；未提供 verdict、trigger 筛选；漏洞库仅显示数量 | 数据量增长后无法查看全量记录，排障效率低 | 增加分页/总数、verdict 与 trigger 筛选、漏洞库条目浏览 |
| RV-28 | 静态检测能力边界未声明，非 UTF-8 未覆盖 | 规则仅对 UTF-8 文本生效；不解析 base64/hex 载荷；不分析二进制；文档仍使用「病毒/木马」表述 | 用户对检测能力预期过高；UTF-16/latin1 脚本、编码载荷可绕过 | 文档明确「静态规则预判，非杀毒引擎」；增加常见编码解码 pass；规划 YARA/沙箱能力 |
| RV-29 | 维度状态语义不一致 | 低危 finding 会让维度状态为 `warn`，但处置为 ALLOW；空库维度为 `pass` | 控制台出现「告警但通过」，用户难以理解 | 维度状态增加 `unknown`/`info`；低危统一为 `info`；UI 增加图例 |

## 七、落地可行性与预期收益评估

### 7.1 可行性

- **技术栈一致**：复用现有 `tar`、`adm-zip`、`node:sqlite`，不引入新依赖，内网部署无障碍；
- **改造面可控**：P0/P1 集中在 `security.service.ts`、`vuln.service.ts`、`rules.ts`、`import.service.ts` 与错误输出，不需要变更对外发布协议；
- **渐进落地**：可先修 RV-01/RV-02 恢复可用性，再引入 lockfile 解析与异步扫描；
- **风险点**：异步化会改变接口时延语义，需要产品确认「上传等待扫描」还是「上传后置扫描 + 状态轮询」；建议保持同步阻断作为默认，异步仅用于复检。

### 7.2 预期收益达成度

| 目标 | 达成度 | 说明 |
| --- | --- | --- |
| 恶意/敏感/权限/行为风险前置拦截 | 85% | 规则覆盖主要模式；嵌套与编码载荷存在绕过 |

## 八、复审要求

### 8.1 整改优先级

| 优先级 | 范围 | 完成标准 |
| --- | --- | --- |
| P0 | RV-01、RV-02 | 代码修复 + 回归用例 + 生产配置演练（`requireSignature=true`、宽区间依赖） |
| P1 | RV-03 ~ RV-16 | 完成率 ≥80%，其中 04/05/06/07/09/11/12 必须完成；接口与文档同步 |
| P2 | RV-17 ~ RV-29 | 纳入下一迭代，不阻塞复审 |
| P3 | RV-30 ~ RV-34 | 作为优化 backlog |

### 8.2 复审专项回归清单

1. `SECURITY_REQUIRE_SIGNATURE=true`：签名包上传 → 定时复检 → 仍为 verified/ALLOW，无隔离；
2. 依赖区间：`lodash: ^4.17.21` + advisory `<4.17.21` 不隔离；锁定 4.17.20 时隔离；
3. 200MB 高压缩比 zip：快速拒绝，进程内存不超过设定上限，事件循环无明显阻塞；
4. 嵌套归档二层含 MAL-001：整体 BLOCK；
5. strict 批量含 1 个被拦截包：零条入库，批次状态明确；
6. npm 403 响应包含 top 3 findings、整改建议与报告短链；PyPI 同样可获得 `scanId`；
7. CSV 中 `=cmd`、`+1`、`@x` 单元格被中和；
8. 空漏洞库：整体 WARN/UNKNOWN，不产生 ALLOW 合格标识；
9. 并发复检：第二个请求返回 409，无重复记录；
10. 性能基线：按确认后的包大小档位输出 P95 扫描耗时与内存峰值。

### 8.3 复审结论模板

- 通过：P0/P1 全部闭环，10 项专项回归通过 → 允许进入下一开发阶段；
- 有条件通过：P0 闭环、P1 完成 ≥80%，剩余项有明确排期 → 允许进入开发但安全模块需在提测前补齐；
- 不通过：任一 P0 未闭环或专项回归失败 → 维持冻结，重新修订。
